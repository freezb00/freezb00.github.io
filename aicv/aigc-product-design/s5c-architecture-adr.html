S5c 架构决策记录 (ADR)

2026-09-17 · 端云协同设计与大文件工程折中

ADR-001：拒绝全云端ADR-002：SAM 2 + 专精修复模型

本文档记录了 Handoff 系统在端云架构协同上的关键技术决策（ADR）。
生成式视觉管线必须在超大工程文件（2GB+ PSD）解析、内存溢出（OOM）防御与云端算力调度之间取得极端的平衡。以下是系统最终采用的架构选型与废弃方案推演。

01ADR-001：计算负载的端云割裂分配

决策：绝不允许 100% 资产上云，强制推行“瘦 API 调用 + 本地组装”。

背景与痛点： 商业原画 PSD 动辄 1.5GB ~ 2GB。如果为了用 AI 处理，让画师先等待 10 分钟把原文件传到云端，处理完再下载 2GB，这个产品必死无疑。
最终方案 (Trade-off)：

  • 端测 (Client/PS Local)： 负责 1) 图层数据维护 2) 超大文件切片压缩 3) 最终 CMYK/PDF 的无损拼合打包 4) 基础色域热力图渲染。
    收益：用户无须上传 GB 级原文件，确保绝对的数据隐私与零网络卡顿感。
  • 云侧 (Cloud/GPU API)： 仅接收画师框选的低分辨率切片区（如 512x512 的 Base64 编码图），在此区域上运行 SAM 2 抠图掩码与 Inpainting 补底预测，仅回传那块极小的“补丁图”至端侧合并。
    收益：GPU 计算带宽占用极低，极速响应。

02ADR-002：AI 模型组合栈选型

决策：放弃微调巨型生成模型 (如 SDXL/Flux)，采用组合工具链 (SAM 2 + 开源专精修补模型)

背景与痛点： 团队一开始想用最新的巨型扩散模型来“直接根据 Prompt 重新生成没文字的背景”。
为什么被否决？ 违背了 S0 定义的“商业图纸原汁原味原则”。商业插画已经定稿，生成模型每次运算都带有创造性的“随机抖动”（改变细节）。
最终方案 (Trade-off)：

  • 分割层 (Segmentation)： 接入开源的 Segment Anything 2 (SAM 2)。其 Zero-shot 能力能以极高精度分离前景文字和特效，且速度极快。
  • 修复层 (Inpainting)： 接入专精于局部修补的模型（如 LaMa / 改进版 SD Inpainting），将注意力强约束在遮罩区域，不碰画面的其他一根草。

03ADR-003：OOM 宕机防御网

决策：建立严格的内存巡检与降级保护链，杜绝宿主崩溃。

在 Photoshop UXP (V8 JS 引擎) 中运行繁重的图像处理极易 OOM。
我们制定了如下工程规约：

  1. 内存探针： 执行一键解耦前，先拦截检查系统 Available RAM 与 PSD Layer Count。若画布宽超 8000 像素，自动在内存中采样成 1K 小图送算 AI 模型。
  2. 瓦片化渲染 (Tiling)： AI 补底大面积纹理时，不进行整图运算，采用 512x512 Tiling 分治处理最后融合边缘。
  3. 崩溃兜底 (Graceful Degradation)： 捕捉所有 API 请求超时与内存栈溢出异常，UI 层不再转菊花，而是闪出一个 [本地安全模式]，降级只提供免 GPU 依赖的基础交付功能（普通打包+存证）。
